# Running the Watermark Simulation: Step-by-Step Runbook

Nov 18, 2026

This is a manual runbook. It takes you from an empty database to the last test scenario, by hand. Each step says what to do, what it creates, and what you should see. For the theory behind it (how the watermark works, the arrow colours, deactivated activities), see `synapse-watermark-pipeline-guide.pdf`. For each Terraform resource, see `synapse-watermark-terraform-guide.pdf`.

Commands run from the repo root (`hybrid-ingestion-platform`), starting on `dev`.

## The big picture: what flows where

```
SOURCE  (Azure SQL, schema src)   CONTROL  (same DB, schema etl)       TARGET  (ADLS, container "synapse")
src.Submissions   500 rows  -+    etl.WatermarkControl  1 row/table    raw/incremental/src_Submissions/
src.Bids      200,000 rows  -+--> etl.NewTablesStaging  catalogue  --->    yyyy/MM/dd/<runId>.parquet
src.Markets         7 rows  -+    etl.LoadAudit         1 row/load     raw/incremental/src_Bids/...
src.StatusCodes     9 rows  -+    etl.ArchiveLog        1 row/archive  raw/static/src_Markets/part-*.parquet
                                                                       archive/yyyyMMdd_HHmm/
```

You create the source and control tables yourself with SQL scripts. The target needs no setup: the pipeline creates its folders and Parquet files on the first run.

### Which activities talk to which database

This matters when you split row 1 and row 2 into two databases:

| Uses the **source** (row 1) | Uses the **control DB** (row 2) |
| --- | --- |
| *Copy New Tables Metadata* (source query reads the catalogue) | *Copy New Tables Metadata* (sink `etl.NewTablesStaging`) |
| child *NewWatermark* (`MAX(ModifiedDate)`) | *Insert New Tables*, *Lookup1*, *Lookup_Large_Tables*, *Lookup1_copy1*, *Lookup Row Counts* |
| child *Delta copy*, static child *Full copy* | child *OldWatermark*, *Update watermark*; static child *Record static load*; `pl_archiving` *Log archive* |
| *Run Loop Static Load* notebook: reading `src` tables | *Run Loop Static Load*: reading `etl.WatermarkControl`, `usp_RecordStaticLoad`; *Notebook1*: `etl.LoadAudit` |

In the replica both columns use `ls_sql_rto`, and the notebooks use one JDBC URL. Splitting means a second linked service for the right-hand column, and a second set of connection parameters in the notebooks. The catalogue query in *Copy New Tables Metadata* would also need to move to the source side, because `etl.vw_SourceTableCatalog` reads the source's `INFORMATION_SCHEMA`.

## Common questions

### How many SQL servers does the simulation use?

**One SQL server, with one database on it.**

| Level | Count | Name |
| --- | --- | --- |
| SQL server | 1 | `sql-wm-dev-<suffix>` (created by Terraform when `deploy_watermark_test = true`) |
| Database | 1 | `rto_watermark_test` (Basic tier) |
| Schemas | 2 | `src` (the pretend source) and `etl` (control tables) |

The source tables, control tables, stored procedures and audit log all live in that one database. That's why there's a single `SQL_SERVER` value, a single linked service (`ls_sql_rto`) and a single JDBC connection in the notebooks.

There's one other "SQL" you'll use, and it isn't a separate server. The Synapse workspace has a built-in **serverless SQL pool** (the `syn-ingest-dev-...-ondemand` endpoint). You use it in Step 7.5 to query the Parquet files with `OPENROWSET`. It holds no tables for the simulation, needs no setup, and is what the platform already uses for `ingest.dbo.orders`.

The client probably uses more than one: their source system and their metadata database are likely separate. To mirror that, add a second server or database and point the control activities at it (row 2 and snippet C above). For testing the workflow, one server is enough.

### What is schema `src`?

A **schema** is a named container inside a SQL database, like a folder that groups tables. Every table belongs to one, and its full name is `schema.table`. `src` is the schema created for the **simulated source system**, the tables the pipeline copies from:

```
rto_watermark_test (database)
+-- src   <- "the client's source system" (pretend)
|   +-- Submissions    500 rows      has ModifiedDate -> incremental
|   +-- Bids       200,000 rows      has ModifiedDate -> incremental, large
|   +-- Markets          7 rows      no watermark     -> full (static) load
|   +-- StatusCodes      9 rows      no watermark     -> full (static) load
+-- etl   <- the pipeline's own bookkeeping
    +-- WatermarkControl, NewTablesStaging, LoadAudit, ArchiveLog
    +-- vw_SourceTableCatalog, usp_* procedures
```

**Why a separate schema.** In the client's world, the source and the control tables live in different systems. Here both share one database to keep the cost down, and the schemas keep them apart:

- `src` stands in for the source. Drop every table in it and you've lost "the source system" and nothing else.
- `etl` belongs to the pipeline, which reads and writes it on every run.
- Discovery only looks at `src` (the view filters on `TABLE_SCHEMA = 'src'`), so the pipeline never tries to copy its own control tables to the lake.

**How the pipeline uses it:**

1. *Copy New Tables Metadata* lists every table in `src`.
2. *Insert New Tables* registers each one in `etl.WatermarkControl` with `SchemaName = 'src'`.
3. The child pipelines build their queries from that, e.g. `SELECT * FROM [src].[Bids] WHERE ModifiedDate > ...`.
4. Lake paths carry the schema name too: `raw/incremental/src_Bids/...`.

`sql/watermark/03_source_seed.sql` creates the schema and fills it. Scenario S4 adds `src.Outages`, to show that any new table created in `src` gets picked up automatically. The name itself has no special meaning (it's short for "source"). The only place that depends on it is the filter in `etl.vw_SourceTableCatalog`. In the client's setup, `src` corresponds to their real source database and schema (row 1 above).

### Is `SQL_SERVER` only for schema `src`?

No. `SQL_SERVER` points to the **server that holds the whole database**, and that one database contains both schemas:

```
sql-wm-dev-<suffix>.database.windows.net     <- SQL_SERVER  (the server)
+-- rto_watermark_test                       <- SQL_DB      (the database)
    +-- src.*   Submissions, Bids, Markets, StatusCodes
    +-- etl.*   WatermarkControl, LoadAudit, ...
```

There's no setting per schema. The pipeline connects once, to server + database, and names the schema in each query: `[src].[Bids]` comes from the `SchemaName` column of the control table, and the `etl.*` names are written into the lookups and stored-procedure calls. The value is written into three places, all for the same connection:

| Where | Used for |
| --- | --- |
| `synapse/linkedService/ls_sql_rto.json` | Every Lookup, Copy and stored-procedure activity: both `src` and `etl` |
| Parent pipeline parameter `SqlServer` | Passed to the two notebooks |
| Both notebooks' parameters cell | Their JDBC connection, which reads `etl.WatermarkControl` and the `src` tables |

You'd only need a second value if you split the source and control into separate databases.

### Where is the folder "RTO Modernization Test"?

It isn't a folder on disk. It's a **display folder inside Synapse Studio**, so you only see it there, once Studio is connected to the repo and switched to your branch (Part 6). Each pipeline, notebook and dataset JSON file contains:

```json
"folder": {
    "name": "RTO Modernization Test"
}
```

Studio uses that property to group the items. The name copies the client's real folder (**RTO Modernization**), with "Test" added so the two are never confused.

| Where it appears in Studio | Contents | Files in the repo |
| --- | --- | --- |
| **Integrate**, Pipelines, **RTO Modernization Test** | the five pipelines | `synapse/pipeline/*.json` |
| **Develop**, Notebooks, **RTO Modernization Test** | `Run Loop Static Load`, `Notebook1` | `synapse/notebook/*.json` |
| **Data**, Linked, Integration datasets, **RTO Modernization Test** | the four datasets | `synapse/dataset/*.json` |

Linked services and the trigger have no folder: they're under **Manage**, Linked services and **Manage**, Triggers.

If the folder doesn't appear, check two things: the Git link is deployed (`synapse_git_repo`, Part 2), and the branch picker shows `watermark/dev-run`. Without the Git link, Studio is in live mode and shows only published items, which is nothing for this pipeline.

### Does the simulation use a self-hosted integration runtime (SHIR)?

**No.** Both linked services connect through `AutoResolveIntegrationRuntime`, the **Azure IR** that Microsoft runs in the cloud, and nothing in `synapse/` references a self-hosted runtime.

| Connection | Runs through | Why no SHIR is needed |
| --- | --- | --- |
| `ls_sql_rto` to the Azure SQL DB | Azure IR | The database is in Azure; the "Allow Azure services" firewall rule lets the Azure IR in |
| `ls_adls_lake` to the storage account | Azure IR | Also an Azure service, reached over Azure's network |
| Notebooks to the SQL DB and the lake | neither IR | Spark connects directly from the pool's nodes, over JDBC and `abfss://` |

The repo does contain a SHIR, `shir-onprem` on your laptop, but it belongs to the **Data Factory** part of the platform (`pl_outbox_to_landing`, reading `C:\outbox`), and it's registered only to the data factory. A Synapse workspace can't use a SHIR registered to a data factory, so your laptop doesn't need to be on for the simulation.

A SHIR only comes in on the client's side, if their real source is the on-prem 1.0 SQL Server: the linked service would become type `SqlServer` with `connectVia` pointing at a SHIR inside their network (row 1 and snippet A above).

## Part 4: Build the source and control tables (about 10 min)

**4.1 Connect** with VS Code mssql or SSMS:

| Field | Value |
| --- | --- |
| Server | `sql-wm-dev-<suffix>.database.windows.net` |
| Authentication | **Microsoft Entra ID - Universal with MFA** (SSMS) / **Microsoft Entra ID** (VS Code) |
| Database | `rto_watermark_test` (**not** `master`) |

SQL logins are disabled; the server accepts Entra ID only. If you get *"Client with IP ... is not allowed"*, your IP no longer matches `allowed_ip`: update it and redeploy.

### 4.2 Run `sql/watermark/01_control_schema.sql`: the control tables

This creates schema `etl`, which holds the tables that drive the pipeline.

**`etl.WatermarkControl`**: one row per source table. It starts **empty**, and the pipeline fills it.

| Column | Meaning |
| --- | --- |
| `ControlId` | ID passed to the child pipeline |
| `SchemaName`, `TableName` | the source table |
| `WatermarkColumn` | e.g. `ModifiedDate`; **NULL means no watermark, so the table gets a full load** |
| `WatermarkValue` | last value loaded; starts at `1900-01-01 00:00:00.000`, so the first run copies everything |
| `LoadType` | `Incremental` or `Static` |
| `IsLarge` | 1 = goes to the large-table loop |
| `IsActive` | 0 = skip this table |
| `LastLoadDate`, `LastRowCount` | filled after each load |

**`etl.NewTablesStaging`**: a scratch copy of the source catalogue (schema, table, watermark column, row count). It's emptied and refilled on every run.

**`etl.LoadAudit`**: one row per table load: run IDs, old and new watermark, `RowsCopied`, plus `LakeRowCount` and `Validated`, which Notebook1 fills.

**`etl.ArchiveLog`**: one row each time archiving runs.

**`etl.vw_SourceTableCatalog`** (view): lists every table in schema `src`. For each one it finds the watermark column (a `datetime` column named `ModifiedDate`, `LastModified` or `UpdatedAt`) and the table's row count.

### 4.3 Run `02_procedures.sql`: the logic the pipeline calls

| Procedure | Called by | Does |
| --- | --- | --- |
| `etl.usp_InsertNewTables` | *Insert New Tables* | Adds staging rows not yet in the control table. No watermark means `Static`; 100,000 rows or more means `IsLarge = 1`. Returns how many it added |
| `etl.usp_UpdateWatermark` | both child pipelines | Writes a `LoadAudit` row, then moves `WatermarkValue` forward |
| `etl.usp_RecordStaticLoad` | static notebook | Writes a `LoadAudit` row for a full load |
| `etl.usp_LogArchive` | `pl_archiving` | Writes an `ArchiveLog` row |

### 4.4 Run `03_source_seed.sql`: the source tables and dummy data

This creates schema `src` and fills four tables with synthetic RTO-style data.

**`src.Submissions`**: standard incremental table, 500 rows.

| --- | --- | --- | --- | --- |

## Part 9: Shut it down when you're finished

1. In Studio: **Monitor**, **Apache Spark applications**, then cancel any running session.
2. On a new branch from `dev`, set `deploy_watermark_test = false` and `deploy_spark = false` (keep `synapse_git_repo` if you'll come back to it), then PR and merge. This deletes the database **and its data**, and the Spark pool. Files in the `synapse` container stay.

Cost while running: about $5/month for the database. Spark bills only while a run is active (3 nodes for the run's minutes).

## If something goes wrong

| Symptom | Fix |
| --- | --- |
| PR `plan` fails on `deploy_watermark_test needs ...` | `deploy_spark` or `reader_object_id` not set |
| PR `plan` fails on `terraform fmt -check` | `dev.tfvars` alignment changed; paste the block from 2.2 again |
| Studio: "You do not have the required permissions" | Step 1.4 missed or done after the deploy: set the variable and re-run the deploy workflow |
| Studio shows no branch picker / no Git | The deploy with `synapse_git_repo` hasn't run, or GitHub isn't authorised yet |
| Lookup or Copy: `Login failed for user '<token-identified principal>'` | `04_permissions.sql` not run, or run with the wrong workspace name |
| Insert New Tables: TRUNCATE permission error | The `GRANT ALTER` line in `04_permissions.sql` didn't run |
| Copy to the lake: 403 | Role assignment still propagating; wait 5 minutes and rerun |
| Notebook: pool not found | `deploy_spark = true` not deployed |
| Error Report: "Invalid URI" | `AlertWebhookUrl` is still `__ALERT_URL__`; paste the webhook.site URL in the Debug dialog |
| Every run copies everything again | `Update watermark` failed in the child; open the child run's output |
